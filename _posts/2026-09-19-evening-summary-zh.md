### [光子发射引导激光故障注入绕过 RP2350 安全调试](https://donjon.ledger.com/blog/rp2350-secure-debug-laser-fault-injection/) ⭐️ 8.0/10

Ledger Donjon 团队公开演示了利用光子发射定位与激光故障注入相结合的方法，绕过树莓派 RP2350 的安全调试保护。该研究针对 RP2350 的安全启动和可信执行场景，说明其安全调试机制并非不可绕过。攻击者需要昂贵设备，但评论指出在家庭实验室以低于 2.5 万美元（甚至低于 1 万美元）的设备即可复现，例如用 PicoEMP 复现 Colin O’Flynn 的 BAM BAM 攻击。社区还讨论了 RP2350 安全飞地作为 Yubikey 替代方案的吸引力，以及安全攻防的持续军备竞赛。

hackernews · synack · 9月18日 16:54 · [社区讨论](https://news.ycombinator.com/item?id=49757050)

**「背景」** RP2350 是树莓派推出的微控制器，内置安全飞地，并可通过一次性可编程（OTP）锁定位永久禁用安全调试（Secure debug）接口；该接口一旦关闭，正常途径无法重新开启。激光故障注入（laser fault injection）是一种物理攻击手段，通过向芯片特定区域照射激光脉冲诱导逻辑产生瞬时错误，从而绕过安全保护；而差分光子发射显微镜（differential photon-emission microscopy）则通过检测晶体管开关时发出的微弱光子，帮助定位芯片内部活跃电路。Ledger Donjon 团队将两者结合：先用光子发射定位调试使能寄存器，再用激光脉冲配合早期复位注入故障，最终在 RP2350 A4 上恢复了本应永久关闭的安全调试访问。

**「影响」** 使用 RP2350 的安全启动和可信执行产品（如安全密钥替代方案）需要重新评估其安全调试保护的有效性，不能将其视为不可绕过的信任根。

**「社区讨论」** 评论者普遍认可披露细节，认为在低于 2.5 万美元（甚至低于 1 万美元）的家庭实验室即可复现，并以 PicoEMP 复现 BAM BAM 攻击为例；也有评论讨论 RP2350 安全飞地作为 Yubikey 替代方案的吸引力、安全军备竞赛，以及对 Raspberry Pi 挑战中 OTP 密钥真实性的疑问。

### [Android 17 被指首次在 3.x 后未向 AOSP 发布新 API](https://grapheneos.social/@GrapheneOS/117282080803799576) ⭐️ 7.0/10

据称 Android 17 是自 Android 3.x 以来首个新增 API 却未同步到 AOSP 的版本；Google 在 Pixel 专属的季度更新中引入新 API，并附带 SDK 与文档，但未向 AOSP 提供对应源码。若属实，这将削弱 AOSP 作为完整公共 API 基线的地位，并影响 GrapheneOS 等基于 AOSP 的替代发行版的兼容性与功能边界。目前证据主要来自 GrapheneOS 的社交平台帖子和社区评论，缺少官方 API 清单及完整技术说明，因此应谨慎对待。该变化可能加剧 Android 开源生态的碎片化，并进一步加深 Google 与 GrapheneOS 等社区项目之间的紧张关系。

hackernews · theanonymousone · 9月18日 19:03 · [社区讨论](https://news.ycombinator.com/item?id=49758736)

**「背景」** Android 开源项目（AOSP）长期被视为 Android 公共 API 的完整基线，Google 通常会在发布新版本时把面向应用开发者的 API 同步到 AOSP，供其他厂商和定制系统使用。GrapheneOS 声称，Android 17 的季度平台发布 QPR1 首次自 Android 3.x（Honeycomb）以来，在没有向 AOSP 发布对应代码的情况下加入了新的应用开发者 API，这些 API 目前仅存在于 Pixel 的系统中，其他 Android OEM 无法使用。由于这些 API 要到 Android 17 QPR2 预计发布时（约 2026 年 12 月）才可能进入 AOSP，因此这一变化可能削弱 AOSP 作为公共 API 基线的作用，并影响 GrapheneOS 等基于 AOSP 的替代发行版。

**「影响」** Android 17 QPR1 首次在 3.x 之后引入未同步至 AOSP 的新 API，这削弱了 AOSP 作为完整公共 API 基线的地位，直接影响 GrapheneOS 等替代发行版的兼容性与功能边界，并可能加剧 Android 生态的碎片化。

**「社区讨论」** 评论普遍认为这是 Google 对 GrapheneOS 等替代发行版设置障碍的又一例证，有用户指出真正问题可能是每年第一和第三季度的 Pixel 专属补丁，而非 API 本身 Pixel 独占；也有用户表达对 Google 开源 stewardship 的不信任，并讨论构建去 Google 依赖的替代生态。

### [Cloudflare 用数学方法再省 100TB 内存](https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/) ⭐️ 7.0/10

Cloudflare 发布技术文章，介绍如何借助数学方法再节省 100TB 内存。文章属于该系列的最新一篇，重点展示在大规模系统中通过算法和数学设计降低内存占用的具体做法，并配有实际案例。这类优化对运行大型基础设施的开发者有直接实用价值，能显著减少资源消耗，但并非颠覆性技术突破。文章延续了 Cloudflare 对内存效率的持续关注。

hackernews · f311a · 9月18日 18:51 · [社区讨论](https://news.ycombinator.com/item?id=49758580)

**「背景」** Cloudflare 的全球网络规模庞大，但资源并非无限，因此团队会持续寻找微小的资源节省方式。这篇文章介绍的是他们如何利用统计学和 Rust 语言，将基于 Pingora 的服务中使用的哈希环（hash ring）虚拟点数量削减约 90%，从而在保持负载均衡效果的同时，回收超过 100TB 的内存。哈希环是分布式系统中用于将请求或数据映射到节点的常见数据结构，虚拟点越多负载越均衡，但内存开销也越大；通过数学方法在均衡性与内存占用之间找到更优平衡，是这次优化的核心思路。

**「影响」** 对于运行大规模基础设施的工程师，这类优化可直接降低内存成本和硬件需求，提高单机可承载的工作负载；具体收益取决于业务场景和现有实现。

**「社区讨论」** 评论普遍赞赏 Cloudflare 重新重视内存优化，认为这种需要数学和工程创造力的工作难以被简单的 AI 生成代码替代；也有评论担心高度优化会让代码库变成难以理解的孤岛，并围绕具体实现（如 Rust 中哈希结构节省 2 字节）提出疑问。
